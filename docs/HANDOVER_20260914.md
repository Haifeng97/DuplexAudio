## 1. 项目是什么

DuplexAudio 用于把普通单轮/多轮中文对话文本转换为全双工对话训练数据。核心产物是：

- 24 kHz、单声道 WAV；
- 按 180 ms 固定 chunk 对齐的 `timeline`；
- 每个 chunk 一个监督目标，目标可能是全双工控制 token、AI 文本 token 或 `<EOR>`；
- 原始对话、人设、场景信息及构造元数据保存在 manifest 行中。

当前主流程会完成文本规范化、去重、场景配比、LLM 辅助构造、玩家语音 TTS、VAD、音频拼接、timeline 生成、异常样本过滤、校验和发布。AI 回复主要作为 timeline 中的目标文本 token，不是训练 WAV 中的 AI 语音。

标签的唯一规范是 [`DUPLEX_LABEL_PROTOCOL.md`](../DUPLEX_LABEL_PROTOCOL.md)。不要仅根据旧数据或脚本名猜测标签语义。

## 2. 最先要知道的结论

1. 新数据优先使用配置驱动入口：`scripts/duplex_pipeline.py`。
2. CPU 数据处理、LLM 请求、格式化和 Viewer 使用 Conda 环境 `duplexaudio`。
3. Qwen3-TTS 使用 Conda 环境 `qwen3-tts`。
4. 当前 TTS 主模型是 `Qwen/Qwen3-TTS-12Hz-1.7B-Base`，本地模型目录为 `/data/haifengjia/models/Qwen3-TTS-12Hz-1.7B-Base`。
5. 默认音频规格是 24 kHz mono，timeline chunk 是 180 ms。
6. TTS 任务是内容寻址且可断点续跑；不要使用 `--overwrite`，除非明确需要清空并重跑。
7. 最终 manifest 大多保存绝对 WAV 路径。只复制最新 manifest 目录不一定能带走音频，必须查看本文件的数据依赖表。
8. 历史合集 `/nfs/shared_data/duplex_balanced_0818/v3/manifest.jsonl` 固定使用 AI Partner v6，不包含 AI Partner v7，也不包含 Rolecard Opening 0818 v1。
9. 交接前积累的生产代码已按功能拆分提交；交接压缩包仍包含同版本代码快照和 `metadata/git-status.txt`，便于脱离远端核对。

## 4. 数据格式契约

每行 manifest 是一个 JSON 对象，关键字段如下：

| 字段 | 含义 |
|---|---|
| `id` | 样本唯一 ID；合并数据前必须检查重复。 |
| `scenario` | 当前样本主场景。 |
| `audio` | 拼接后的训练 WAV，正式数据通常为绝对路径。 |
| `sample_rate` | 当前为 24000。 |
| `chunk_ms` | 当前为 180。 |
| `timeline` | 每个 180 ms chunk 对应的目标标签。 |
| `question_text` / `answer_text` | 当前主轮的文本摘要。 |
| `sysprompt` | 人设和系统上下文。sysprompt 中的历史不参与训练轮次。 |
| `source_row.turns` | 实际对话轮次及完整来源信息。 |
| `source_row.tts_assets` | 构造该样本需要的玩家语音 TTS 资产。 |
| `stats.duration_sec` | 最终训练 WAV 时长。 |
| `label_protocol` | 当前应为 `fd_control_v1`。 |

文本长度统计使用“去掉空白后的 Unicode 字符数”，标点计入。轮数使用 `source_row.turns` 的元素数。

## 5. 标签和场景

固定标签：

```text
<FD_IDLE>
<FD_D_WAIT>
<FD_A_ANSWER>
<FD_F_WAIT>
<FD_G_INTERRUPT>
<FD_H_CONTINUE>
<FD_J_ACTIVE>
<FD_C_INTERVENE>
<FD_I_COMPLETE>
text tokens
<EOR>
```

场景：

| 场景 | 行为 |
|---|---|
| `normal_qa` | 玩家说话时 WAIT，结束后 ANSWER + 回复文本 + EOR。 |
| `incomplete_query` | 半句末尾 F_WAIT，静音后玩家继续说完，再回答。 |
| `incomplete_query_clarification` | F_WAIT 后等待 3-5 秒，J_ACTIVE 主动澄清。 |
| `player_interrupts_ai` | 玩家打断 AI，旧回答无 EOR，新回答重新 ANSWER。 |
| `player_backchannel` | 玩家短反馈触发 INTERRUPT，随后 H_CONTINUE + ANSWER 继续原回复。 |
| `ai_intervenes_user` | 检测到越界内容后 C_INTERVENE + ANSWER 主动制止。 |
| `player_complete` | I_COMPLETE 后简短确认，或按静默分支直接结束。 |

目标主场景比例通常是：normal 70%、interrupt 15%、普通 incomplete 4%、clarification 1%、backchannel 5%、other 5%。`other` 当前主要由 intervene 和 complete 构成。配置可以覆盖比例；AI Partner v7 因没有可用 LLM，明确关闭了 incomplete 和 clarification。

## 9. 新数据标准流程

以下用 `CONFIG` 代表一份从现有生产配置复制并修改的新配置：

```bash
export CONFIG=configs/your_run.json
conda activate duplexaudio
cd /data/haifengjia/Projects/DuplexAudio
```

配置中至少核对：`run_name`、`run_dir`、输入 namespace、场景比例、voice bank、TTS 模型和 release 输出目录。新 run 必须使用新的 `run_name` 和输出目录，不能覆盖旧版本。

### 9.1 规范化与场景计划

```bash
python scripts/duplex_pipeline.py prepare \
  --config "$CONFIG" \
  --resume
```

`prepare` 等价于依次运行 `normalize` 和 `plan`，不调用 LLM 或 TTS。

### 9.2 不完整 Query：在线 LLM 路径

先导出 5 个截断候选：

```bash
python scripts/duplex_pipeline.py llm-export-splits \
  --config "$CONFIG" \
  --resume
```

调用 DSV4：

```bash
export DSV4_API_KEY='由接手人配置'
export DSV4_WSID='由接手人配置'

python scripts/duplex_pipeline.py llm-run \
  --config "$CONFIG" \
  --input runs/<run_name>/03_llm/incomplete_split/requests.jsonl \
  --output runs/<run_name>/03_llm/incomplete_split/results.jsonl \
  --concurrency 2 \
  --resume \
  --quiet
```

当前端点需要 IP 白名单，是否可用必须现场确认；共享服务默认并发用 2。代码不保存实际密钥。当前可用模型名最后一次配置为 `cgame_aimate_generater_1`，旧配置中的 `cgame_aimate_generater` 可能已失效。

然后完成打分和澄清：

```bash
python scripts/duplex_pipeline.py llm-export-rank \
  --config "$CONFIG" \
  --input runs/<run_name>/03_llm/incomplete_split/results.jsonl

python scripts/duplex_pipeline.py llm-run \
  --config "$CONFIG" \
  --input runs/<run_name>/03_llm/incomplete_rank/requests.jsonl \
  --output runs/<run_name>/03_llm/incomplete_rank/results.jsonl \
  --concurrency 2 --resume --quiet

python scripts/duplex_pipeline.py llm-apply-rank \
  --config "$CONFIG" \
  --input runs/<run_name>/03_llm/incomplete_rank/results.jsonl

python scripts/duplex_pipeline.py llm-export-clarification \
  --config "$CONFIG"

python scripts/duplex_pipeline.py llm-run \
  --config "$CONFIG" \
  --input runs/<run_name>/03_llm/clarification/requests.jsonl \
  --output runs/<run_name>/03_llm/clarification/results.jsonl \
  --concurrency 2 --resume --quiet

python scripts/duplex_pipeline.py llm-apply-clarification \
  --config "$CONFIG" \
  --input runs/<run_name>/03_llm/clarification/results.jsonl
```

如果在其他机器离线填文件，保持 `request_id`，把模型输出写入 `response_text`，再把 filled JSONL 传给相应 apply 命令。

不完整 Query 的截断前缀必须少于 15 个有效字符；空白和标点不计入有效字符。旧数据的完整性复核流程见 [`FWAIT_COMPLETENESS_FILTER_PIPELINE.md`](../FWAIT_COMPLETENESS_FILTER_PIPELINE.md)。

### 9.3 无 LLM 路径

保守规则切分：

```bash
python scripts/duplex_pipeline.py offline-apply-splits \
  --config "$CONFIG"
```

配置需要：

```json
{
  "llm": {
    "backend": "offline",
    "offline_split_mode": "conservative",
    "min_incomplete_prefix_effective_chars": 3,
    "max_incomplete_prefix_effective_chars": 14
  }
}
```

该模式只选择明显的悬空句式，覆盖率低但比随机切分可靠。没有 LLM 时更稳妥的生产策略是像 AI Partner v7 一样把 incomplete 和 clarification 比例设为 0，而不是随机截断。

### 9.4 场景物化与 TTS 任务

```bash
python scripts/duplex_pipeline.py materialize \
  --config "$CONFIG" \
  --resume

python scripts/duplex_pipeline.py tts-prepare \
  --config "$CONFIG" \
  --resume
```

`tts-prepare` 会生成：

```text
runs/<run_name>/05_tts/NEXT_COMMANDS.sh
```

这个文件包含本次 run 的精确 TTS、格式化和发布命令。优先使用它，不要从旧聊天记录手抄路径。

### 9.5 TTS

```bash
conda activate qwen3-tts
export PROJECT=Cgame_aimate_haifengjia
```

从 `NEXT_COMMANDS.sh` 运行第一条 `03_run_tts_multi_gpu.py` 命令。当前经验值：

- `batch_size=64`、每卡 2 个进程：更稳妥；
- `batch_size=128`、每卡 1 个进程：速度快，但显存更紧；
- 不要在同一张卡同时使用 `batch_size=128` 和多个进程，除非先小规模验证；
- 任务按估计长度分桶，可用 `--shuffle_batches` 打乱 batch 级顺序；
- 默认自动 resume，已有有效 WAV/结果会复用；`--overwrite` 才会重跑；
- `--max_runtime_sec` 可让任务运行固定时长后停止，并保留完成结果。

查看进度：

```bash
conda activate duplexaudio
python scripts/03_tts_progress.py \
  --work_dir runs/<run_name>/05_tts/run \
  --watch 5
```

worker 的详细输出在 `runs/<run_name>/05_tts/run/logs/`。主终端只维护一个总进度条，不会持续输出每条样本。

### 9.6 格式化和发布

完整 TTS 完成后，在 `duplexaudio` 环境运行 `NEXT_COMMANDS.sh` 中 TTS 后面的命令，或者：

```bash
conda activate duplexaudio

python scripts/duplex_pipeline.py format \
  --config "$CONFIG" \
  --workers 100

python scripts/duplex_pipeline.py release \
  --config "$CONFIG"
```

如果只需要当时已经完成的 TTS 快照：

```bash
python scripts/duplex_pipeline.py finalize-partial \
  --config "$CONFIG" \
  --workers 100
```

`finalize-partial` 会丢弃缺 TTS、无效 WAV、短于阈值、相对文本异常过长或接近生成上限的场景，再格式化并发布。它不会要求 TTS 全部完成。

浏览器访问：`http://<服务器 IP>:8765`。通过 SSH 端口转发时可保持默认 `127.0.0.1`：

```bash
ssh -L 8765:127.0.0.1:8765 <user>@<server>
```

注意：Viewer 启动时会为每个 manifest 建立内存索引。不要一次加载 100 GB 级合集，否则启动慢且占用大量内存。大数据先抽样，或只加载需要查看的分开版。

当前允许读取音频的根目录：项目目录、`/nfs/haifengjia`、`/nfs/shared_data`。新增其他根目录需要修改 `tools/duplex_viewer.py` 中的 `ALLOWED_AUDIO_ROOTS`。

如果端口被占用：

```bash
lsof -nP -iTCP:8765 -sTCP:LISTEN
```

只终止确认是本项目 Viewer 的 PID，不要按端口或 Python 进程名盲目批量 kill。

## 13. Resume、覆盖和版本规则

- `duplex_pipeline.py ... --resume` 根据 `runs/<run_name>/run_state.json` 跳过已完成 stage。
- 如果配置或输入发生变化，不要依赖旧 stage 状态；使用新 `run_name`，或明确清理对应 run 后重做。
- `llm-run --resume` 按 `request_id` 跳过 `status=ok` 的结果。
- TTS 默认按内容 fingerprint 复用；文本、参考音频、参考文字、模型、语言、采样率或生成参数变化都会产生新 fingerprint。
- `03_run_tts_multi_gpu.py --overwrite` 会忽略 resume 结果，生产环境默认不要使用。
- formatter/release 会写目标 manifest。正式发布必须追加新版本目录，不覆盖旧版。
- 旧版 manifest 经常复用更早版本 WAV；删除旧版前必须扫描最新 manifest 的音频路径。

## 14. 已知风险和容易踩坑的地方

1. **历史临时文件。** 当前机器有未跟踪的 `.orig` 备份；不要把它们当作主版本或批量提交。
2. **依赖未锁定。** 两个 Conda 环境存在，但没有正式 environment lock。
3. **LLM 服务不稳定。** 需要 IP 白名单、环境变量凭据，模型名可能变化；支持离线填 JSONL。
4. **TTS 显存。** batch 128 很快，但多进程容易 OOM；错误任务可以缩小 batch 后 resume。
5. **异常长音频。** 过去出现接近生成上限、只有语气词或拖长发音的样本。当前 runner 和快照流程会按时长上限过滤，但仍需要抽听。
6. **动作描述污染切分。** interrupt/intervene 的 overlap 只能根据真实回复文本计算，不能把括号动作描述当语音文本。Rolecard v1 已做对应修复。
7. **VAD 与标签对齐。** incomplete、interrupt、backchannel 需要 trim TTS 首尾静音后再拼接，否则事件标签可能早于玩家真实开口。
8. **大 manifest。** `customized_0811_0817/v2` 约 91 GB，合集约 111 GB；避免普通编辑器打开，使用流式脚本、`rg`、`head`、分块统计。
9. **绝对路径。** 跨机器需要同样挂载 `/nfs/shared_data`，或复制 WAV 后流式重写 `audio`。
10. **数据权利。** CPED/CharacterEval 有上游许可证和第三方内容风险；CharacterEval 用于训练会污染同名评测。
11. **敏感内容。** `ai_intervenes_user` 有意包含辱骂、骚扰等文本，分发和训练日志需注意。
12. **来源失衡。** Customized 0811+0817 在历史合集占约 75.8%，训练时建议按 source/scenario 采样，而不是只做全局 shuffle。

## 15. 发布检查清单

- 新版本目录，不覆盖旧 manifest/WAV。
- `id` 非空且全局唯一。
- `audio` 全部存在，可在目标机器访问。
- WAV 为 24 kHz mono PCM16。
- `len(timeline) * chunk_samples` 与 WAV sample 数一致。
- `label_protocol=fd_control_v1`。
- 每个场景只出现允许的事件标签。
- incomplete 前缀少于 15 个有效字符，且人工抽查确实不完整。
- interrupt 旧回复没有 EOR，backchannel 有 H_CONTINUE。
- clarification 有 F_WAIT 和 J_ACTIVE。
- intervene 的回答确实与剩余玩家语音重叠。
- complete 静默分支在 I_COMPLETE 后没有 ANSWER/TEXT/EOR。
- TTS 缺失、过短、异常过长、触顶和 ASR 不一致样本已过滤。
- 每个场景至少随机听检 20 条；长音频、上限附近音频单独抽检。
- 保存 config、run_state、stats、rejected 原因和最终校验报告。
